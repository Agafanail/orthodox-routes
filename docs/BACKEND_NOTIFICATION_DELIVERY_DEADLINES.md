# Notification lease deadlines and recovery

The existing secret-protected internal worker now claims one notification immediately before dispatch, rather than letting later messages consume a batch lease while earlier provider calls run. Prepared six-language email and minimal push payload, recipient preferences, business-event atomicity, delivery idempotency, scheduled events, and the existing five-attempt/backoff policy remain unchanged. No provider, scheduler, environment setting, UI, or production operation is activated.

## Application boundary

The application calls service-only `api.notification_worker_claim_job_v3(lease, channels)`, which returns one JSON job or null with authoritative `evaluated_at` and `lease_until`. It derives remaining time from relative database durations minus the entire monotonic claim round trip, not synchronized host clocks. Missing/expired/invalid timing, an unconfigured channel, or fewer than twenty seconds remaining prevents sending. Each subsequent claim has a fresh lease key; the existing optional deterministic first-lease hook remains for tests. The unit-count limit remains 1–50, not a guarantee that a whole HTTP batch fits a particular hosting deadline.

Enqueue/claim/completion waits are bounded to five seconds; the default protected client also aborts requests at five seconds. Provider waits are bounded to twelve seconds, with the existing independent selected-adapter limits. Unsafe application origins fail before enqueue or destination leasing. The origin is credential-free HTTPS without path/query/fragment, not a caller-selected return URL.

Only fixed adapter identity, HTTP status class, known safe failure classes, and a strict successful email UUID acknowledgement reach completion. Push references remain null. Unknown/private adapter fields, exceptions, malformed success, and timeouts become a fixed temporary failure, never raw diagnostics. Actual selected Resend/VAPID results keep their existing classifications. No provider body, destination/key, message, or arbitrary error is returned in statistics or logged.

## PostgreSQL boundary

Migration `20261019150000_notification_delivery_deadlines.sql` preserves the legacy claim signatures/column shapes and existing complete API. Legacy claim helpers also enforce the existing attempt ceiling and refuse terminal delivery states; they cannot overflow the structural counter after abandoned leases. Claim deadlines use actual evaluation time. The new narrow JSON bridge is the only application claim path, with at most two known configured channels and no extra ordinary-role access. All helpers remain ungranted, with hardened definer paths and bounded lock waits.

Completion locks outbox then delivery, samples time only after both waits, and refuses an expired/stale lease or terminal authoritative delivery. A provider webhook's delivered/permanent/suppressed result cannot be overwritten by a late worker acknowledgement or a reclaim. The delivery-update predicate also rechecks terminal state after an intervening row wait. Rejected completion does not change retry state, subscriptions, preferences, or the underlying ride transaction.

Before claiming, v3 reconciles at most fifty eligible expired/queued terminal-or-exhausted jobs under skip-locked outbox locks and locked delivery rows. Already authoritative terminal delivery is preserved byte-for-byte while its outbox is settled. Abandoned/exhausted work without an authoritative terminal result becomes a dead-letter delivery with one minimized operational alert, never a sixth dispatch or counter overflow. The recovery does not invalidate a push subscription or alter preferences merely because an abandoned lease had an unknown external outcome. Existing successfully completed failure/terminal-subscription handling is otherwise unchanged. These are delivery records, not new complaint/audit retention or moderation rules.

## Compatibility, verification, and limits

Apply the additive migration before the application. An application against a missing v3 bridge fails closed, without falling back to unbounded legacy claims. Older deployed workers retain their old application-side behavior; coordinate/drain them in an owner-controlled rollout. A timeout does not prove remote cancellation, exactly-once delivery, or rollback. Existing provider idempotency, fresh leases, retry limits, and post-lock checks govern recovery; there is no automatic RPC retry after an uncertain result.

No-network tests cover fixed results, private diagnostic exclusion, origin refusal, both clock-skew directions, claim-latency subtraction, sequential single claims, configured channels, invalid/short leases, and abort-ignoring enqueue/claim/send/completion. Disposable PostgreSQL integration separately covers real outbox/delivery waits across expiry, source rollback, stale reclaim, fifth-attempt success, abandoned/exhausted bounds and legacy counter protection, terminal preservation, authenticated push setup with unchanged subscription/preferences after abandonment, and actual migration/ACL replay. Exact synthetic rows/alerts/subscription are removed; no remote data is touched. SQL proof is pending mandatory CI when Docker is unavailable locally.

No real email, push handset/browser acceptance, hosting-capacity measurement, scheduler activation, production migration, or provider account/configuration is verified by these fixtures. Review actual hosting batch/runtime limits before activation; individual operation bounds do not establish whole-batch latency or capacity.
