# Explicit complaint mailbox verification boundary

## Inactive composition

The provider-independent verification broker and unregistered HTTP controller complete the path from an explicit same-origin POST to the existing target-bound `api.verify_complaint_email_draft_v2(uuid,text)` operation. A displayed route UUID is supplied separately by the server; the body accepts only `emailToken`, never an actor, mailbox, target, replacement UUID or privileged operation name. No registered Next.js route, email-page UI, provider, secret or operational setting is activated.

GET/HEAD/OPTIONS and link-scanner visits perform no verification. Query strings, cross-origin requests and unsupported body metadata are refused. The existing bounded complaint JSON reader enforces its 64 KiB UTF-8/JSON ceiling and five-second read deadline; parsed data remains untrusted. A future browser page must obtain the existing `email-proof` fragment, remove it from navigation/history as appropriate, show the same draft reference and wait for an explicit confirmation press. It must not consume a proof on page load or put it into query strings, logs, analytics or referrers. Actual browser/proxy/mailbox acceptance remains required before registration.

The broker requires an explicit protected client, dedicated server rate secret and one trusted hosting/proxy address. It never reads forwarding headers, cookies, Auth sessions or environment defaults. No address means unavailable, not a caller-supplied fallback. Verification may occur without an account; mailbox proof never signs in a user, associates a new actor, changes account contacts or receives a complaint.

## Separate attempt budgets

Migration `20261022130000_complaint_verification_boundary.sql` adds five nullable verification settings to the existing protected security policy. All are unset by default and a constraint refuses partial/unsafe configuration. Exact deployment values remain an owner-controlled gate under Backend Architecture §20. Structural window/count ceilings are safeguards, not approved settings.

Service-only `consume_complaint_verification_rate_limit(network_key,draft_key)` atomically consumes global, network and draft dimensions. These are independent from preparation/mailbox budgets. A failed dimension rolls back all updates; global denial cannot accumulate arbitrary identity rows. Policy reads are locked, a short shared advisory lock serializes counts, and database time is sampled after waits. Only HMAC-SHA-256 network/draft keys with separate verification/scope domains are stored, never raw IP, draft reference, mailbox, proof, secret or report text. Network normalization preserves equivalent IPv6 and IPv4-mapped spellings. New policy versions are required when changing settings or rotating the rate secret.

Each explicit verification attempt first requires the fixed `allowed` result, then calls v2 with the same expected UUID and current proof. Missing policy, uncertain/failed budget acknowledgement or denial prevents the proof RPC. Every repeat spends a fresh attempt; a budget result is not a reusable execution capability. Each RPC has an independent five-second aborting wait, the controller contains a stalled injected broker at eleven seconds, and no automatic retry occurs. Budget and verification are deliberately separate transactions: a consumed budget is not refunded after a later refusal/timeout. A verification may already have committed when its acknowledgement is lost; v2 retains its existing idempotency and original expiry.

`expire_complaint_verification_rate_buckets(limit)` removes only expired windows, in bounded batches of 1–100 under the same lock. Counters have forced RLS and no ordinary/service table grants; both new hardened definer APIs are service-only with empty search paths and five-second lock waits. Reapplying the migration preserves existing policy values, counters and ACL. Cleanup of ephemeral attempt windows is not a received-complaint/audit retention decision. Maintenance scheduling remains a prerequisite for activation.

## Safe outcomes and verification

The only success is `email_verified` for the expected UUID; `expired` is terminal draft metadata, not receipt of a complaint. Null/unknown/superseded/mismatched proof shares one rejected result. Strict three-field receipt parsing rejects extra data, wrong UUIDs, pending/unexpected states, unzoned/impossible dates and normalized 24:00. The existing retry codec and preparation broker reuse this calendar parser. The controller returns only fixed status and minimal UUID/expiry, with private/no-store, no-referrer and no cookie/Auth changes. Exceptions and provider/database diagnostics never reach responses.

No-network tests exercise the actual broker/controller with synthetic RPC seams, HMAC scope/canonicalization, fixed outcomes, GET/query refusal, same-origin/body validation, budget-before-proof ordering, explicit-repeat budgets, immutable input snapshots, wrong-target/private result containment and abort-ignoring deadlines. Disposable PostgreSQL integration separately verifies every budget dimension, one-winner concurrency, rollback/late-error atomicity, actual advisory waits across expiry, bounded cleanup, null defaults, grants/forced RLS and actual migration replay. Existing targeted-proof integration verifies the real SQL proof transition and its races. Synthetic sequencing is not an activated end-to-end browser or mailbox test.

The [protected maintenance bridge](BACKEND_COMPLAINT_MAINTENANCE.md) now composes bounded draft/counter expiry behind its own empty-by-default scheduler secret; actual environment/scheduling remains required. Public registration, trusted proxy configuration, approved operational limits, resend budgets/handling, received cases, owner delivery/review, retention choices and actual provider/browser testing remain unfinished. Existing target visibility/reporting windows, proof-mail rotation, fifteen-minute draft ceiling, Auth and transport behavior are preserved. No dependency or production operation changes.
