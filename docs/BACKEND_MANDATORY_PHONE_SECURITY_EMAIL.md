# Mandatory phone-change security email

Backend Architecture §12 separates ordinary ride-email preferences from mandatory account-security mail. The existing `account.phone_changed` source notification previously used the ordinary preference at enqueue and could also be suppressed by a later preference change. Migration `20261022140000_mandatory_phone_security_email.sql` corrects only that mismatch.

The ungranted immutable helper `app.notification_requires_security_email(text)` recognizes exactly the existing `account.phone_changed` event. It does not treat every account/church event or caller-selected prefix as mandatory. The existing notification creator may enqueue this email with ordinary ride email off; both preference-suppression predicates preserve it. No ordinary application/service role gains permission to invoke the classifier or create arbitrary notifications. The existing authenticated SMS-confirmed source transition still determines the actor, event, safe target and recipient.

The current verified Auth/contact/destination guard is explicitly required and retained. Missing/unverified/stale email never becomes a destination merely because an event is mandatory. All legacy/v3 leasing, deadlines, retries, provider validation and webhook terminal-state authority remain unchanged. Push stays opt-in. Neither saved preference nor effective ordinary external-channel eligibility changes: mandatory security mail does not make an opted-out account eligible for a new ride action.

Event/localization keys, prepared six-language copy, payload minimization, source idempotency, priority and existing retention are unchanged. This does not choose a longer security-history/audit retention period, enqueue historical mail, reactivate terminal suppressed jobs, configure a provider or claim real delivery. Future mandatory event types require an explicit reviewed extension rather than an unrestricted wildcard.

The disposable phone-verification suite disables both ordinary channels before a real authenticated phone-code verification RPC after recent reauthentication. Its code comes from a synthetic local worker fixture, not real SMS or handset delivery. It checks exactly-once source history, an email job despite opt-out, unchanged preferences/contact, preservation during a later ordinary preference toggle, ordinary ride-email suppression, current-destination service-only v3 leasing, synthetic temporary completion without any provider acceptance claim, classifier grants and actual migration/definition/ACL replay. The parent restores its original preference and deletes only its exact synthetic identities; extra test notification rows are cleaned exactly. Existing verified-email integration separately tests stale bindings and post-lock source changes.

No new UI, dependency, operational limit, provider, public write API or production operation is introduced. Real mailbox/provider acceptance and legally approved retention remain separate release work. Ordinary enqueue/opt-out concurrency beyond this mandatory-event exception is not claimed to be redesigned by this slice; existing lock ordering is preserved.
