# Account deletion confirmation and mail preparation

This slice implements protected deletion-intent/email-consent preparation for IA 20.4, its restricted-account permission in IA 46.4, and the recent-authentication requirement in Backend Architecture section 15. It does not execute account deletion. No sender, scheduler, public confirmation page, provider, session revocation, transport closure, administration intake, anonymization, ledger or retention is activated. A confirmed intent is not a deleted account and cannot authorize destructive processing without fresh authoritative checks in that future workflow.

`ops.deletion_request` contains an Auth subject reference, one successful client key, purpose state/timestamps, hashed current-email binding and proof, plus bounded mail-attempt/lease metadata. Forced RLS and revoked direct table access apply to ordinary, service and church-operator roles. No mailbox, phone, name, location, comment, clear proof or clear lease is stored. The Auth reference permits a verified pre-account subject to request deletion of its own Auth data without creating an application account. An existing incomplete/restricted account needs no phone, adult declaration, Terms acceptance or ordinary ride channel for this privacy operation. Mutation/delivery validate current Auth standing/binding; deleting/deleted application standing is refused by the shared actor boundary.

The authenticated APIs accept no target actor. `request_account_deletion_confirmation(client_key)` requires recent signed Auth reauthentication for a new intent. It serializes by subject, locks Auth/account/contact in order and validates the current verified Auth mailbox against the protected copy when an application account exists. The binding includes that mailbox and confirmation/contact-email versions, expressed with timezone-independent epochs; login timestamps, phone and notification preferences do not invalidate it. Same-key retry returns the same safe acknowledgement, never a new job. A different key while an intent remains active is refused rather than falsely acknowledged without recording that key. An expired or identity-invalidated old key cannot reactivate a purpose. The shared AMR/policy calculation is factored into an ungranted internal time-parameter helper; its existing zero-argument wrapper preserves statement-time behavior, signature, STABLE/invoker/empty-path mode and grants. New consent calls supply database clock time after waits. No API accepts caller-selected time, no factor/policy value changes and no phone-flow behavior change are introduced.

`current_account_deletion_confirmation()` returns only the current subject's latest versioned request UUID, safe status, proof expiry and confirmation time. Its read-only projection treats logically expired pending confirmation as unavailable before cleanup. It returns no source hash, mailbox, subject identity, proof, lease or delivery metadata. Existing authenticated account export adds only that account's minimized intent history and dates through an ungranted helper and narrow subject-history index, preserving all prior sections and state/ownership guards. Pre-account status does not fabricate an application profile to enable that existing profile-export API. The private-read lifecycle regression now includes a present synthetic confirmation record and rejects its projection in deleting/deleted application standing while preserving restricted access; cleanup removes only that exact synthetic record/audit.

The service-only single-job claim discovers a pending candidate before locking, then takes the same subject/Auth/account/contact/request order and rechecks state, identity binding and absolute time after waits. Only a current requested mailbox reaches the delivery material. A fresh 256-bit proof is returned transiently; only its SHA-256 hash is stored. A supplied UUID lease is hashed, lasts at most 45 seconds and is clamped to the 15-minute confirmation deadline. A retry rotates the proof and job; old letters cannot verify a new proof or different request. Claims are bounded at five attempts, including abandoned final-lease recovery. There is no automatic mailbox retarget, hidden resend, preference change or sixth dispatch. Last uncertain-delivery proof can still be verified before its purpose expires. Mail is mandatory consent material, independent of optional ride email/push settings; no provider acceptance is implied.

The service completion accepts only fixed sent/temporary-failure/permanent-failure outcomes, with fresh request/lease checks after row waits. Unknown/stale acknowledgements return false and cannot reactivate a closed/confirmed purpose. The separate bounded expiry function clears only elapsed unconfirmed capabilities/leases; it cannot erase confirmed consent as a retention shortcut. Fifteen minutes is a technical proof lifetime, not an account/audit retention policy. No cleanup schedule is configured.

`confirm_account_deletion_email(request_uuid, proof)` requires the same Auth subject and matching current request/proof/email binding. A new successful confirmation also requires recent reauthentication. Expiry is evaluated after the request lock; GET/scanner requests cannot perform this volatile mutation. Confirmation atomically records consent and closes mail leasing, leaving Auth, profile, contacts, phone verification, church roles and all transport unchanged. Exact confirmed retries acknowledge the prior fact without a second event. A mutating re-check closes pending or confirmed intent when its email binding changed rather than transferring consent to a new mailbox. The old proof remains unavailable if source state is later restored. Read-only status/history is a fact projection, never execution authorization.

Successful request and email confirmation each add one minimized atomic audit fact targeting the opaque request UUID. They contain only fixed action/field names, actor/system classification and transaction/time metadata, with no Auth subject ID copied into a public target, contact, proof, lease, case narrative or private payload. A pre-account fact uses system classification with subject attribution retained only in the protected intent; no fake application account is created for audit compatibility. Existing account actor references are used when available. Unsuccessful proof attempts do not fabricate success. Late failures roll back consent/audit together.

Disposable CI verification uses fresh actually signed-in synthetic Auth identities, real own/cross-subject RPCs, same-key and worker concurrency, role/table/helper grants, pre-account and restricted/incomplete states, safe projections and timezone canonicalization. It exercises proof rotation, late rollback, current-email change during an actual Auth-row wait, actual purpose/lease row-wait expiry, idempotent confirmation, logical status/maintenance, bounded abandoned mail, source-state-only soft-deletion refusal and actual migration/ACL replay. Synthetic mail material stays in memory and only opaque fingerprints/booleans are asserted on failure. Exact intent/audit/profile/Auth fixture cleanup is mandatory. PR #97 CI `41041814295` and main CI `41042674513` passed all four required jobs and cleanup/post-steps. These are SQL/Auth contracts, not real mailbox, sender, scanner-page/browser or completed-deletion proof. Local Docker remains unavailable.

## Prepared server sender

`processDeletionProofMail` consumes only the fixed deletion-confirmation claim/completion APIs, using the existing selected Resend adapter. It shares the proven mail-proof runner with complaints: typed static purpose definitions, one fresh lease at a time, validated service material, relative database deadlines minus the monotonic claim round trip, five-second claim/completion aborts, twelve-second provider bound, a full twenty-second dispatch/completion reserve, strict provider acknowledgement and fixed completion outcomes. Returned counters never contain a contact, capability, provider reference or private error. A null single-candidate claim is not proof of a drained queue. The existing complaint exports, parsed shape, prepared text, destination, completion semantics and limits are preserved. Literal-calendar validation stays in a pure module, separate from server/provider imports.

The versioned prepared email covers all six supported languages and asks the subject to review and confirm the deletion request. No account/ride/complaint/name/contact/location is interpolated into the body. Its destination is the approved `/{lang}/profile` context, with the opaque request and email proof only in `#deletion-request=...&email-proof=...`; no secret reaches a path/query or ordinary transition HTTP log. Recipient email is solely the provider destination. Credential-free HTTPS origin validation applies before any claim. Synthetic transport tests exercise the actual selected Resend request/acknowledgement code, not a real mailbox. No route, scheduler, secret, provider setting or public control invokes this sender. Before activation, the browser must consume/remove the fragment privately, require the same authenticated subject and an explicit action, and connect the confirmed request to the complete approved lifecycle. Opening a link must never itself consume consent or claim deletion completed.

Remaining work includes sender activation with the explicit confirmation page/action, genuine mailbox/staging acceptance, the last-administrator intake/resume integration, automatic active-object closure and agreement cancellation, session/push revocation, private-data removal/anonymization, the separate deletion ledger/restore path, legally approved retention and final cutover. Destructive processing must recheck current identity/binding, memberships and all relevant domain state; it cannot trust an impact snapshot or historical case alone. An initial/final administrator case does not require the user to manually cancel every trip.
