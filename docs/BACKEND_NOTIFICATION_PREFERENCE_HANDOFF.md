The disposable causal regression on `e9b917c` failed in CI `40849530446`: a creator read ordinary email enabled, paused before inserting its notification, and the authenticated preference RPC committed opt-out while no notification/job existed. Resuming the real creator produced a late queued email; the selected v3 worker still returned its destination. No delivery row was manufactured and no provider was called. The failure compared booleans, not private payloads.

The forward migration adds a final current-source check to the selected single-job `api.notification_worker_claim_job_v3`, after the existing helper locks and verified Auth/contact source waits. It uses fresh statements inside the existing `VOLATILE` function, not another preference/subscription row lock or a producer-side lock that could invert the existing source/preference/outbox order. PostgreSQL's [snapshot rules](https://www.postgresql.org/docs/17/xfunc-volatility.html) explain why the separate statement matters; actual concurrency verification remains required, not replaced by the reference.

Ordinary email requires its current saved flag. Push requires the current saved flag and the same recipient's still-active subscription. The existing exact `account.phone_changed` security-email classifier bypasses only ordinary email opt-out, never verified-current-address checks or push consent. A disallowed selected job/delivery is atomically suppressed with the existing fixed safe failure code and cleared lease; no destination is returned. A known `sent_at` provider fact is instead reconciled as sent without changing provider facts or handing it out again, including bounded recovery at the attempt ceiling. Existing delivered/permanent-failure/suppressed terminal recovery is preserved. No preference, subscription validity, eligibility, source ride, message copy, contact binding, retention, dependency, grant or provider configuration changes.

The change applies to the selected v3 bridge used by the current application worker. Historical batch signatures remain compatibility-only; they are not the current dispatch path. Already handed-off provider requests cannot be recalled; existing in-flight preference-update behavior is unchanged. A refusal returns null and ends that bounded worker pass; a later invocation can process the next job. No unbounded draining or new scheduler is introduced.
